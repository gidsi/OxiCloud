## `docs/backlog/001-basic-calendar-sync.md`
```markdown
# 🥇 Priority 1: Basic Calendar Sync (CalDAV MVP)

**As a** privacy-conscious self-hoster,  
**I want to** connect my calendar clients (Thunderbird, DAVx5, GNOME Calendar) to my OxiCloud account to sync my events,  
**so that** I can manage my schedule securely across all my devices without relying on Big Tech.

**Context for the Squad:** 
This is the core engine. We need to handle basic authentication, calendar discovery, and full CRUD (Create, Read, Update, Delete) of `.ics` events in a single default calendar per user. Do not split this up. A synced calendar must be fully functional.

**Acceptance Criteria:**
```gherkin
Scenario: Client successfully connects and discovers the default calendar
  Given the user "alice" has an active OxiCloud account
  When the client (e.g., Thunderbird) queries the user's CalDAV principal URL with valid credentials
  Then the server successfully authenticates the request
  And the server returns the path to "alice"'s default calendar collection

Scenario: Two-way sync of a new event
  Given the user's client is connected to their default OxiCloud calendar
  When the user creates a new event "Dentist Appointment" on the client
  And the client pushes the event to the server
  Then the OxiCloud server stores the event securely
  And when a second authenticated client requests calendar updates, the server returns the "Dentist Appointment" event

Scenario: Deleting an event across devices
  Given an event "Lunch meeting" exists in the user's default OxiCloud calendar
  When the user deletes the event on their mobile client (DAVx5)
  And the mobile client syncs the deletion to the server
  Then the OxiCloud server removes the event from the active calendar collection
  And the server instructs other connected clients to remove the event during their next sync
```

**🛠️ Codebase/Rust Constraints (Architecture):**
*   **Axum Presentation:** Use `axum 0.8.9` extractors for Basic Authentication. Route WebDAV HTTP methods (`PROPFIND`, `REPORT`, `PUT`, `DELETE`) strictly in the presentation layer. WebDAV XML requests/responses must be parsed/serialized here using an async-friendly library like `quick-xml`.
*   **Domain:** Define an `Event` aggregate root. It must not contain WebDAV or HTTP-specific data.
*   **Infrastructure (SQLx 0.8.6):** Store `Event` entities in a PostgreSQL `events` table (columns: `id`, `user_id`, `ical_uid`, `ical_data` (TEXT/BYTEA blob), `etag`, `updated_at`). Use `tokio` for concurrency handling during sync requests. Provide SQLx-managed ETags for concurrency control and WebDAV sync-tokens.

**🔒 Security Constraints (Security Reviewer):**
*   **Auth & Transit:** Enforce TLS/HTTPS (typically at the reverse proxy) so Basic Auth credentials are encrypted.
*   **Authorization:** All `sqlx` queries must strictly filter by `user_id == authenticated_user.id`. 
*   **Input Validation:** XML parsing must explicitly disable External Entity Resolution (XXE) to prevent Server-Side Request Forgery (SSRF) and local file disclosure. Set a strict payload size limit via Axum (e.g., 5MB) on `.ics` uploads to prevent DoS.
*   **Path Traversal:** Validate the `{event.ics}` path parameter so users cannot traverse directories (e.g., `../`).

**⚠️ Tech Lead Synthesis & Risks:**
*   **Risk:** iCal (`.ics`) parsing is notoriously complex due to timezones and recurring events.
*   **Mitigation:** Treat `ical_data` as an opaque blob in the backend as much as possible. Only extract what is absolutely necessary for WebDAV metadata (like the UID and generating an ETag). Leave business logic and scheduling interpretation to the clients.
```

## `docs/backlog/002-basic-contact-sync.md`
```markdown
# 🥈 Priority 2: Basic Contact Sync (CardDAV MVP)

**As a** privacy-conscious self-hoster,  
**I want to** sync my address book to OxiCloud via CardDAV,  
**so that** I have all my friends' and colleagues' contact details on my phone and desktop without giving that data to Google or Apple.

**Context for the Squad:** 
Similar to Priority 1, but for vCards. Users need a reliable default address book. DAVx5 on Android and Apple Contacts on iOS/macOS are the primary targets here.

**Acceptance Criteria:**
```gherkin
Scenario: Syncing a new contact from client to server
  Given the user is authenticated on their client (e.g., DAVx5) via CardDAV
  When the user creates a new contact "Bob Smith" with phone number "555-0100"
  And the client syncs the address book
  Then the OxiCloud server stores the parsed vCard data securely in the default address book
  And the contact "Bob Smith" is available for download by any other of the user's connected devices

Scenario: Updating an existing contact propagates correctly
  Given the contact "Bob Smith" exists in the OxiCloud address book
  When the user updates the phone number to "555-0200" on their desktop client
  And the client pushes the updated vCard to the server
  Then the server overwrites the existing vCard with the new data
  And the server accurately updates the sync token/ETag so other clients know to fetch the update
```

**🛠️ Codebase/Rust Constraints (Architecture):**
*   **Axum Presentation:** Expose endpoints for CardDAV (`PROPFIND`, `REPORT`, `PUT`, `DELETE`). Implement `addressbook-multiget` REPORT for efficient batch syncing of vCards.
*   **Domain:** Define a `Contact` aggregate root.
*   **Infrastructure (SQLx 0.8.6):** Create a `contacts` table (columns: `id`, `user_id`, `vcard_uid`, `vcard_data`, `etag`, `updated_at`). Ensure `sqlx` connection pooling (via Axum State) is leveraged to handle multiple concurrent device syncs seamlessly.

**🔒 Security Constraints (Security Reviewer):**
*   **Payload Size Limits:** vCards often contain base64 encoded profile pictures. Enforce a sensible max size in Axum (`axum::extract::DefaultBodyLimit`) to prevent memory exhaustion, while allowing high-res photos (e.g., 10MB limit).
*   **Tenant Isolation:** As with calendars, strict `user_id` validation must happen at the SQLx query level to prevent a user from querying another user's vCard UIDs.
*   **XML Hardening:** Same XXE protections apply for CardDAV XML reports.

**⚠️ Tech Lead Synthesis & Risks:**
*   **Risk:** Loading huge address books into memory during a `multiget` report could cause memory spikes or block the Tokio executor.
*   **Mitigation:** Use `sqlx` streams to fetch large amounts of contacts from PostgreSQL and stream the XML response back through Axum asynchronously, rather than buffering the entire response in memory.
```

## `docs/backlog/003-client-auto-discovery.md`
```markdown
# 🥉 Priority 3: Frictionless Client Auto-Discovery 

**As a** non-technical user or busy self-hoster,  
**I want to** simply enter my server domain and login credentials into Apple Calendar or DAVx5,  
**so that** my calendars and contacts configure themselves without me having to type out massive, obscure server URLs.

**Context for the Squad:** 
Apple Calendar is notoriously stubborn. If we don't implement `.well-known` URIs, users will think our server is broken because they won't know they have to manually type full explicit paths. This routes Axum to handle `/.well-known/` gracefully and bridges the gap between "technically works" and "actually usable."

**Acceptance Criteria:**
```gherkin
Scenario: Apple Calendar / DAVx5 auto-discovery bypasses manual URL entry
  Given the user wants to add their OxiCloud account to a native client
  When the client sends a GET/PROPFIND request to `/.well-known/caldav` or `/.well-known/carddav`
  Then the server intercepts the request
  And the server responds with an HTTP redirect (301 or 302) to the correct CalDAV/CardDAV root URL
  And the client successfully prompts for credentials and completes setup without manual path configuration
```

**🛠️ Codebase/Rust Constraints (Architecture):**
*   **Axum Presentation:** Implement routes for `/.well-known/caldav` and `/.well-known/carddav`.
*   **Protocol Handling:** These handlers must return an `axum::response::Redirect` (HTTP 301 or 302). It should redirect to a unified service root or the specific user's principal URL.
*   **Domain/Infra Leakage:** None. This is entirely an HTTP/Axum routing concern. No database interaction is required for the `.well-known` endpoints themselves.

**🔒 Security Constraints (Security Reviewer):**
*   **Open Redirect Prevention:** Ensure that the redirect targets are hardcoded to our service root paths (e.g., `/dav/`) and do not accept any user input that could be manipulated to redirect clients to a malicious domain.
*   **Auth Challenges:** Ensure the target of the redirect requires authentication, so the client receives a HTTP 401 Challenge, prompting the user for credentials.

**⚠️ Tech Lead Synthesis & Risks:**
*   **Risk:** Apple Calendar and DAVx5 have different fallback mechanisms. Apple Calendar sometimes uses `PROPFIND` directly on `.well-known` endpoints instead of `GET`.
*   **Mitigation:** Bind both `GET` and `PROPFIND` methods to the `.well-known` Axum route handlers to ensure maximal compatibility.
```

## `docs/backlog/004-multiple-calendars-address-books.md`
```markdown
# 🏅 Priority 4: Multiple Calendars & Address Books

**As a** busy professional,  
**I want to** create and manage multiple separate calendars (e.g., Work, Personal, Family) and address books,  
**so that** I can keep my schedules and contacts organised and toggle their visibility separately in my client.

**Context for the Squad:** 
Now that the engine works, we need to let users organise their lives. If a client sends a command to create a new calendar collection, the server must support it via PostgreSQL structural boundaries, strictly enforcing user data isolation in `sqlx`.

**Acceptance Criteria:**
```gherkin
Scenario: Client provisions a new secondary calendar
  Given the user already has a default calendar synced via CalDAV
  When the user instructs their client to create a new calendar named "Work Deadlines" with the color Red
  And the client sends the creation request to the OxiCloud server
  Then the server provisions a new distinct calendar collection for that user
  And the server saves the metadata (name: "Work Deadlines", color: Red)
  And the user can save events specifically into "Work Deadlines" without them appearing in the default calendar

Scenario: Independent address book syncing
  Given the user has created a secondary address book named "Coworkers"
  When the client requests a sync of only the "Coworkers" address book
  Then the server returns only the vCards stored in "Coworkers"
  And the server does not return contacts from the default personal address book
```

**🛠️ Codebase/Rust Constraints (Architecture):**
*   **Axum Presentation:** Add support for the `MKCALENDAR` method (CalDAV extension of `MKCOL`) and standard `MKCOL` for CardDAV.
*   **Domain:** Introduce `Calendar` and `AddressBook` entities. Update `Event` and `Contact` aggregates to reference their parent collection.
*   **Infrastructure (SQLx 0.8.6):** Create `calendars` and `address_books` tables. Add `calendar_id` to `events` and `address_book_id` to `contacts`. Implement Foreign Keys with `ON DELETE CASCADE`. Track `sync_token` at the collection level, incrementing it via database triggers or application logic whenever a child entity changes.

**🔒 Security Constraints (Security Reviewer):**
*   **Deep Authorization:** When modifying an event/contact, verify that both the item AND its parent calendar/address book belong to the authenticated user.
*   **XSS & Input Sanitization:** Validate and sanitize client-provided metadata like calendar `name` and `color` (e.g., enforce strict hex-code format for colors) to prevent Stored XSS when this data is rendered in web interfaces later.
*   **Resource Limits:** Implement a quota in the application layer limiting the total number of calendars/address books a user can create (e.g., 50) to prevent database flooding.

**⚠️ Tech Lead Synthesis & Risks:**
*   **Risk:** Routing collisions and N+1 query problems. With dynamic paths like `/{user}/calendars/{calendar_id}/{event.ics}`, route definitions can become overlapping and complex. Fetching multiple collections and their entities can degrade performance.
*   **Mitigation:** Use strict Axum path extractors. For database operations, rely heavily on `sync_token` diffing. Clients should only ask for what has changed since the last token, ensuring queries remain fast and lightweight. Do not fetch all events from the database; only fetch the ETags during a standard `PROPFIND` collection query.
```
