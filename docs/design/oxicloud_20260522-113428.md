# Final Architectural Review and Approved Design Documents
**Epic: Automated Reliability Guarantees for DAV Sync (Testing & CI)**
**Author:** Tech Lead

## 1. Summary of Changes Made
Following the integration of security audits, Developer B's data model review, QA framework validations, and my architectural sign-off, the following key adjustments have been made to the initial designs:

*   **Concurrency & ETags (Story 4):** Removed the over-engineered HMAC wrapping for ETags based on Developer B's feedback. We will use a raw monotonic DB `version` integer combined with strict Optimistic Concurrency Control (OCC) at the SQL layer, mapping to a structured `Err(ModelError::Conflict)` to cleanly return HTTP 412.
*   **Data Models & Sync State (Story 2):** Introduced Tombstone records (`deleted_at`) to correctly support `<sync-collection>` 404 responses for deleted contacts. Switched to Keyset Pagination (`WHERE ulid > $last_seen_ulid`) to prevent offset drift during active syncs.
*   **Security & Resource Limits (Stories 1 & 5):** Added model-level caps on iCalendar `RRULE` (recurrence) expansions to prevent algorithmic DoS. Added strict Unicode Normalization (NFC) for all stored paths to prevent lock/file duplications across OS types.
*   **Performance & TTLs (Stories 1 & 5):** Enabled SQLite WAL mode in CI to prevent `SQLITE_BUSY` test flakiness. Shifted from background TTL sweep jobs to Lazy TTL Evaluation (`expires_at > NOW()`) for WebDAV Locks.
*   **Protocol Compliance (Story 3):** Standardized on `HTTP 301 Moved Permanently` (instead of 308) to ensure legacy iOS `dataaccessd` compatibility.

# Final Approved Design Documents

## Design Document 1: Thunderbird Calendar Sync Stability
**Objective:** Guarantee Thunderbird CalDAV compatibility on updates via automated offline tests.

### 1. Architecture and Component Design
*   **Infrastructure Testing:** Isolated test suite using `actix_web::test::TestRequest` to replay raw Thunderbird HTTP fixtures (`PROPFIND`, `PUT`) rapidly without TCP overhead.
*   **Data Persistence:** Transient `sqlx::SqlitePool` per test. **Requirement:** Enforce `PRAGMA journal_mode=WAL;` and `PRAGMA synchronous=NORMAL;` to prevent database locking during parallel CI execution.
*   **Security Limiter:** `quick-xml` integrated strictly with external entities (DTDs) disabled. Enforce a strict Actix `PayloadConfig` size limit (5MB) and an XML nesting depth limit to stop "Billion Laughs" XML Bombs.
*   **Model Restrictions:** iCalendar `RRULE` parsing must include a hard cap on recurrence expansions (e.g., maximum 500 instances or 5 years) to prevent CPU DoS. Storage must explicitly use standard UTC formats (Epoch/ISO8601).

### 2. API Contracts and Error Handling
*   Input accepts raw Thunderbird payloads; responds matching RFC 4791 namespaces exactly (`DAV:`, `CALDAV:`).
*   If payload parsing encounters a DTD, immediately returns `400 Bad Request` and logs a security exception.

## Design Document 2: Guarantee DAVx5 Contact Sync (No Data Loss)
**Objective:** Perfect WebDAV Sync (RFC 6578) with DAVx5 using sync-tokens.

### 1. Architecture and Component Design
*   **Testing Strategy:** Stateful E2E integration test using a background `tokio::spawn` Actix server and `reqwest` to simulate DAVx5's continuous sync loop.
*   **Infrastructure Layer (`CardDavRepository`):**
    *   **Tombstones:** Do not hard-delete contacts. Use a `deleted_at` timestamp so `REPORT` requests can return accurate `<DAV:response>` 404s for removed items.
    *   **Tokens:** Use Monotonic ULIDs for `sync_token`. 
*   **Pagination:** Implement Keyset Pagination (`WHERE ulid > $last_seen_ulid LIMIT 100`) to guarantee stable data transmission without offset skipping.
*   **Security (IDOR):** Database queries must rigidly append `WHERE owner_id = $auth_user_id AND sync_token = $provided_token`. Requests mapped to a mismatched user ID must trigger a `403 Forbidden` or `404 Not Found`.

### 2. API Contracts and Error Handling
*   Responses include only `<D:response>` elements for changed/deleted contacts.
*   If an extremely outdated sync-token is provided (beyond tombstone retention limits), server replies with `<DAV:valid-sync-token-or-not-found>` (HTTP 403), forcing DAVx5 to re-baseline.

## Design Document 3: Flawless Apple Calendar & Contacts Discovery
**Objective:** Zero-configuration Apple auto-discovery using `.well-known` endpoints.

### 1. Architecture and Component Design
*   **Infrastructure Routing:** Lightweight handlers in `infrastructure/web/routes.rs`. 
*   **Protocol Strictness:** Use `HTTP 301 Moved Permanently` (not 308) for maximum compatibility with legacy iOS `dataaccessd` daemons.
*   **Security Configuration:** Base URLs for the 301 Redirect must be strictly derived from static server configuration (`web::Data<AppConfig>`). **Host header must be ignored** to prevent Open Redirect vulnerabilities.
*   **Stateless Tenant Mapping:** The database will not maintain redirect state. Tenant mapping is calculated deterministically via `domain -> principal_template` mapping.

### 2. Test Plan
*   Use `TestRequest` to simulate `iOS/16.0 (19A346) dataaccessd/1.0` User-Agents.
*   Validate exact XML paths for `<current-user-principal>`, ensuring valid `CTag`/`ETag` headers exist. Assert that path traversal attempts (`../../`) are neutralized by routing.

## Design Document 4: Safe Concurrent Edits (Preventing Conflict Data Loss)
**Objective:** Protect against conflicting offline edits using strict ETags.

### 1. Architecture and Component Design
*   **Domain & ETag Mapping:** Drop HMAC cryptography. Utilize a raw `version` integer (or high-precision `updated_at` microsecond timestamp) on the DB row. The Application layer formats this into an opaque ETag string (e.g., `W/"version-123"`).
*   **Concurrency Mechanism:** Optimistic Concurrency Control (OCC) at the SQL layer: `UPDATE resources SET data = $1, version = version + 1 WHERE id = $2 AND version = $3`.
*   **Error Abstraction:** If `0` rows are affected, the Infrastructure layer returns `Err(ModelError::Conflict)`, which the Actix middleware natively translates to a standard `412 Precondition Failed`.
*   **Testing Strategy:** `tokio::sync::Barrier` interleaving two `sqlx::Transaction` blocks ensures a deterministic race condition test without relying on network latency.

### 2. Security Considerations
*   OCC strictly prevents Time-of-Check to Time-of-Use (TOCTOU) race conditions.
*   Using abstract `version` integers prevents information disclosure regarding system-wide update frequencies (compared to exposing exact timestamps).

## Design Document 5: Assure General Compatibility (Litmus Integration)
**Objective:** Pass 100% of the core RFC 4918 `litmus` conformance test suite.

### 1. Architecture and Component Design
*   **Testing Infrastructure:** Docker Compose pipeline running the compiled `litmus` C-binary against a test-flagged OxiCloud container.
*   **State Management (WebDAV Locks):** Locks will persist in a dedicated `webdav_locks` SQL table. This ensures multi-node stateless compatibility for production deployments.
*   **Data Integrity (Unicode):** The SQL repository **must** normalize all incoming URIs to Unicode NFC (Normalization Form C) prior to querying or saving to prevent Apple (NFD) vs. Linux (NFC) duplication glitches.

### 2. Security Limiting
*   **Lazy TTL:** Instead of background crons, locks are validated via lazy evaluation: `WHERE expires_at > NOW()`.
*   **Depth Bombs:** Intercept `PROPFIND` requests with `Depth: infinity`. Cap recursive responses at Depth 1 unless explicitly overridden by configuration to prevent CPU lockups.
*   **Lock Quotas:** Restrict active locks per user account (e.g., max 50). Exceeding this quota triggers `429 Too Many Requests`.
*   **Path Traversal Check:** `COPY` and `MOVE` endpoints must sanitize the `Destination` header, asserting against `../` malicious escapes.
