# OxiCloud Final Design Documents & Review: DAV Reliability & CI

**Status:** Approved for Implementation
**Author:** Tech Lead
**Stack:** Rust, Axum 0.8.9, SQLx 0.8.6 (PostgreSQL 16), Tokio

---

## 1. Summary of Changes Made
Based on the comprehensive PO, Tech Lead, and Security reviews, the initial design drafts have been revised to address all identified architectural, consistency, and security risks. The following critical changes have been incorporated into these final implementation documents:

*   **Atomic DAV Mutations:** All CalDAV and CardDAV mutations (`PUT`, `DELETE`) are now strictly wrapped in `sqlx::Transaction` blocks. This guarantees atomic increments of `ctag` and `sync_token` values alongside opaque blob updates, preventing client sync fractures.
*   **Method-Preserving Redirects:** The `.well-known` client discovery endpoints now exclusively return `308 Permanent Redirect` or `307 Temporary Redirect` (with explicit `Cache-Control` headers) to prevent HTTP method downgrades on `PROPFIND` requests.
*   **Open Redirect Prevention:** Redirect `Location` headers are constructed strictly from the server's internal `BASE_URL` environment variable. Client-provided `Host` headers are ignored.
*   **Stateless WebDAV Locks:** The proposed in-memory WebDAV lock manager was rejected. WebDAV locks will be strictly PostgreSQL-backed via `sqlx` with strict expiration timeouts to maintain horizontal scalability and prevent lock-abuse DoS.
*   **Opaque Data Persistence:** Both CardDAV (vCard) and VTODO payloads will be stored as opaque `bytea` blobs. The application layer will only extract routing metadata (like `UID`) using safe parsing to guarantee zero data loss of non-standard client properties.
*   **Strict Security Mitigations:** 
    *   XML parser (`roxmltree`) is explicitly configured to disable DTD and external entity resolution to prevent XXE/Billion-Laughs attacks.
    *   `Depth` headers on `PROPFIND` are strictly limited to `0` or `1` to prevent depth-bomb DoS attacks.
    *   WebDAV temporary chunk directories will be aggressively cleaned up by a mandatory `main.rs` boot-time purge sequence, addressing Tokio thread panic edge cases.
    *   Axum `DefaultBodyLimit` is enforced on all DAV mutation routes to prevent memory exhaustion from maliciously large payloads.

## 2. Final Design Documents (Updated with Security & Test Strategies)

### Story 1: (P1) Automated Client Discovery (.well-known)
*(Promoted from P2 to P1 due to high user value and low complexity)*

*   **Architecture & Routing:** Pure stateless Axum 0.8.9 routing. No database interaction is required.
*   **API Contracts:**
    *   `GET /.well-known/caldav` -> `308 Permanent Redirect` to `/caldav/v2/{user_id}/`
    *   `GET /.well-known/carddav` -> `308 Permanent Redirect` to `/carddav/v2/{user_id}/`
*   **Security Mitigations:**
    *   **Open Redirect:** The destination URL is built exclusively using the trusted `BASE_URL` env variable.
    *   **Cache Poisoning:** Responses will include `Cache-Control: no-cache, no-store`.
*   **Testing Strategy:**
    *   Use `tower::ServiceExt::oneshot` to bypass the network stack for sub-millisecond unit testing.
    *   **Test Cases:** Assert strictly on `StatusCode::PERMANENT_REDIRECT`/`TEMPORARY_REDIRECT` to ensure no 302 downgrades. Inject a malicious `Host: evil.com` header and assert the `Location` header remains localized to the trusted domain. Verify GNOME Calendar discovery payloads.

### Story 2: (P1) CalDAV Sync Reliability (Thunderbird & Apple Calendar)

*   **Architecture & Routing:** Axum extractor middleware validates `Authorization` against PostgreSQL. Requests are routed to `/caldav/v2/{user_id}/*`.
*   **XML Parsing & Response:** `roxmltree` is configured securely (no external entities). Responses strictly enforce the `urn:ietf:params:xml:ns:caldav` namespace.
*   **Data Models:** `calendars` table (`ctag`, `sync_token`) and `calendar_objects` table (`icalendar_data` as bytea). All mutations (`PUT`/`DELETE`) occur within a `sqlx::Transaction`.
*   **Security Mitigations:**
    *   **XXE Prevention:** DTD and external entities explicitly disabled.
    *   **Depth Bombs:** `Depth` header is validated at the application boundary; values other than `0` or `1` yield `403/400`.
    *   **Payload Exhaustion:** `axum::extract::DefaultBodyLimit` applied to drop oversized XML before parsing.
*   **Testing Strategy:**
    *   Use `#[sqlx::test]` for isolated DB state per test, binding an Axum router to `127.0.0.1:0` (`tokio::spawn`) and testing via `reqwest`.
    *   **Test Cases:** Assert exact XML namespace structure against Apple Calendar PCAP fixtures. Perform full Thunderbird CRUD flow, asserting `sync_token` increments. Inject XXE payloads to assert `400 Bad Request` drops.

### Story 3: (P1) CardDAV Mobile Contact Integrity (DAVx5 & iOS)

*   **Architecture & Routing:** `/carddav/` routing isolated from CalDAV, utilizing shared `infra::dav_xml` multi-status response generators.
*   **Opaque Storage:** vCards (v3.0/v4.0) are treated as opaque `bytea` blobs. Only the `UID` is extracted for routing. `unwrap()`/`expect()` are banned during extraction; invalid VCards return `400 Bad Request`.
*   **Security Mitigations:**
    *   **Cross-Tenant Isolation (IDOR):** The `{user_id}` path parameter is strictly validated against the authenticated principal. Mismatches yield `404 Not Found` to prevent user enumeration.
*   **Testing Strategy:**
    *   Reuse CalDAV `#[sqlx::test]` integration harness.
    *   **Test Cases:** Execute full CRUD with captured DAVx5 (vCard 4.0) payloads. Push an iOS vCard 3.0 with custom `X-APPLE-*` properties and assert a 1:1 byte match on read. Test cross-tenant isolation by authenticating as User A and requesting User B's endpoint, asserting `404 Not Found`.

### Story 4: (P3) VTODO Tasks Sync Reliability

*   **Architecture & Routing:** Reuses CalDAV protocol. Updates `PROPFIND` `<supported-calendar-component-set>` to support `VEVENT` and `VTODO`. 
*   **Storage:** Stored as an opaque blob in `calendar_objects`. DB status extraction is deliberately omitted to maintain consistency with the zero-loss strategy.
*   **Security Mitigations:**
    *   Memory limits via `axum::extract::DefaultBodyLimit` are enforced specifically for VTODO PUT requests to prevent memory exhaustion from large embedded attachments.
*   **Testing Strategy:**
    *   Snapshot testing via the `insta` crate for complex XML response validation.
    *   **Test Cases:** Assert state transition (e.g., `STATUS:NEEDS-ACTION` to `STATUS:COMPLETED`) by issuing sequential `PUT` requests and verifying the `sync-token` increments, followed by fetching the blob to assert string updates inside the VTODO iCalendar data. Test payloads from both Apple Reminders and OpenTasks.

### Story 5: (P2) Native WebDAV File Operations
*(Demoted from P1 to P2 to isolate risk of Lock Manager scope)*

*   **Architecture & Routing:** Stream processing via `axum::body::Body::from_stream` to disk chunks, followed by atomic move to permanent storage inside a `sqlx::Transaction`. 
*   **DB-Backed Locks:** WebDAV `423 Locked` states managed via a `webdav_locks` PostgreSQL table with strict expiration intervals.
*   **Security Mitigations:**
    *   **Path Traversal:** Strict path parsing rejects any `.` or `..` URI segments with `400 Bad Request`.
    *   **Disk DoS (Temp Files):** A mandatory startup cleanup routine in `main.rs` purges the temp upload directory before the Axum listener binds.
*   **Testing Strategy:**
    *   Compliance testing via the industry-standard WebDAV Litmus suite in CI.
    *   **Test Cases:** Spawn concurrent Tokio tasks simulating uploads/deletes to assert `423 Locked` responses. Attempt `PUT /webdav/v1/user/../../../etc/passwd` to verify rejection. Simulate an aborted upload (drop `reqwest` connection) and verify Tokio `io::Error` triggers temporary file deletion.

## 3. Confirmed Testing & CI Strategy

The CI Pipeline will utilize GitHub Actions and `cargo nextest` to execute a multi-staged verification process:

```yaml
stages:
  1_Static_Analysis:
    - cargo clippy --all-targets --all-features -- -D warnings
    - cargo fmt --all -- --check
    - sqlx prepare --check # Enforces compile-time SQL/DB schema match
  
  2_Fast_Tests:
    - cargo nextest run --lib # Pure unit tests, tower routing, client discovery redirects
  
  3_Integration_Tests:
    - services: postgres:16-alpine
    - steps:
      - sqlx database setup # Runs migrations
      - cargo nextest run --test '*' # Ephemeral port Axum servers, #[sqlx::test] isolated DBs, XXE tests
  
  4_Compliance_Suites:
    - services: postgres:16-alpine
    - steps:
      - start_test_server_in_background
      - run: make litmus-suite # Executes WebDAV Litmus against the live test server
```

**Operational Requirements for Deployment:**
1.  **Health Check:** A `/health` endpoint validating `sqlx::PgPool::acquire` and temp filesystem writability.
2.  **Graceful Shutdown:** Tokio SIGTERM handling to allow active WebDAV upload streams to terminate safely.
3.  **Startup Purge:** Implementation of the WebDAV temporary chunk cleanup sequence in `main.rs` before server start.

## 4. Final Review Comments (Tech Lead Sign-Off)

**Architecture Fit:** Verified. The adherence to Axum 0.8.9 routing standards, pure SQLx 0.8.6 transaction logic, and Tokio asynchronous execution fits seamlessly into our existing domain, application, and infrastructure layers. Moving away from stateful in-memory features (like the WebDAV locks) back into PostgreSQL ensures we retain horizontal scalability.

**Code Quality & Technical Coherence:** Verified. The decision to embrace "opaque blob" storage for unstructured client data (vCards, VTODOs) while utilizing strictly structured databases for synchronization metadata (sync-tokens, CTags) is an elegant compromise. It prevents over-engineering, guarantees zero client data loss, and keeps our domain logic exceptionally clean. 

**Security & Risk:** Addressed. By explicitly validating XML parsers against XXE, strictly bounding DB/XML depth queries, capping payload sizes, and mitigating WebDAV Temp-file Disk exhaustion via both Drop traits and boot-time sweeps, the platform's threat profile is well mitigated. 

**Decision:** These designs are **Approved for Implementation.** The team may proceed with development using the documented CI and testing boundaries.
