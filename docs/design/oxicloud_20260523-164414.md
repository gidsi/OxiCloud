## docs/backlog/001-deep-health-check.md
```markdown
# Priority 1: Deep Health Check for Uptime Monitoring

**Context:** Self-hosters use tools like Uptime Kuma, Docker auto-heal, or reverse proxies. A simple "200 OK" from the web server isn't enough; if the PostgreSQL database or the filesystem drops, users can't sync their calendars or files. We need the health check to verify the actual underlying infrastructure.

**User Story:**
As a Server Admin, I want to query a deep health check at `/health` so that my monitoring tools know exactly when my database or file storage goes offline and can alert me before my users experience sync failures.

**Acceptance Criteria:**
```gherkin
Scenario: System is fully operational
  Given OxiCloud is running
  And the PostgreSQL database is reachable
  And the configured local storage backend is writable
  When a monitoring tool makes a GET request to `/health`
  Then the server returns a 200 OK status code
  And the response body contains JSON indicating all subsystems (database, storage) are "healthy"

Scenario: PostgreSQL database is unreachable
  Given OxiCloud is running
  But the PostgreSQL database connection drops or times out
  When a monitoring tool makes a GET request to `/health`
  Then the server returns a 503 Service Unavailable status code
  And the response body contains JSON indicating the database subsystem is "unhealthy"

Scenario: Storage backend is read-only or unreachable
  Given OxiCloud is running
  But the storage directory loses write permissions or unmounts
  When a monitoring tool makes a GET request to `/health`
  Then the server returns a 503 Service Unavailable status code
  And the response body contains JSON indicating the storage subsystem is "unhealthy"
```

**Security Constraints (Security Reviewer):**
*   **Information Disclosure:** The JSON response must *not* leak underlying database error messages, stack traces, or internal server file paths. Only return generic subsystem states (e.g., `"database": "unhealthy"`).
*   **Resource Exhaustion / DoS:** Frequent polling of `/health` must not become a vector for denial of service. The endpoint needs a rate limiter, or the health check results must be cached.

**Technical & Architectural Constraints (Codebase/Rust Expert):**
*   **Axum State:** Inject the `sqlx::PgPool` and app configuration via `axum::extract::State`.
*   **SQLx Pattern:** Verify the database connection by executing a lightweight query: `sqlx::query("SELECT 1").execute(&pool).await`. Do *not* use a full table query. Implement a strict timeout (e.g., 2 seconds) via `tokio::time::timeout` so the endpoint doesn't hang indefinitely if the DB connection drops silently.
*   **Non-blocking I/O:** The storage write-check must use `tokio::fs` or `tokio::task::spawn_blocking` to prevent blocking the async reactor. Avoid generating garbage files if possible; check permissions metadata first.

**Tech Lead Risk Synthesis & Mitigation:**
*   **Risk:** If 5 monitoring nodes ping `/health` every 10 seconds, we are constantly triggering disk I/O and DB queries, which degrades actual sync performance.
*   **Mitigation:** We will implement a background `tokio::task` that polls the DB and Storage every 5 seconds and updates a shared `std::sync::Arc<tokio::sync::RwLock<HealthStatus>>`. The `/health` endpoint will simply read this lock, achieving sub-millisecond response times and completely mitigating the DoS risk on our infrastructure layers.
```

## docs/backlog/002-metric-stability.md
```markdown
# Priority 2: Metric Stability (Cardinality & Memory Safeguards)

**Context:** We cannot ship an observability feature that doubles as a Denial of Service (DoS) vulnerability. Self-hosters expose their instances to the open internet, meaning bots will scan random, non-existent URLs. If we dynamically create a metric label for every URL requested, OxiCloud will consume all server memory and crash, interrupting file and calendar sync.

**User Story:**
As a Server Admin, I want OxiCloud's metrics collection to enforce strict static labels and memory limits so that my server stays online and doesn't crash from Out-Of-Memory (OOM) errors when bots or scanners spam random URLs.

**Acceptance Criteria:**
```gherkin
Scenario: Preventing cardinality explosion from random paths
  Given OxiCloud is actively collecting HTTP request metrics
  When a bot makes GET requests to 500 unique, non-existent paths (e.g., `/wp-admin`, `/does-not-exist-123`)
  And a monitoring tool makes a GET request to `/metrics`
  Then the HTTP metrics group all these invalid requests under a single static label (e.g., `route="unmatched"`)
  And a new label is NOT generated for each unique bad path

Scenario: Respecting metrics memory limits under attack
  Given OxiCloud is configured with a strict memory limit for its metrics registry
  When an attacker attempts to force metric variation through complex, varied query parameters
  Then the metrics registry drops new metric variations once the memory threshold is reached
  And OxiCloud continues to successfully process user sync requests (PROPFIND, PUT) without crashing
```

**Security Constraints (Security Reviewer):**
*   **OOM Vulnerability strictly forbidden:** Input data (User-Agent, query string parameters, raw URI paths, client IPs) must *never* be used as metric labels. All labels must be predefined enums or static strings.
*   **Safe Handling of 404s:** All 404 Not Found requests must be aggregated under a single tag variant (e.g., `route="404"` or `route="unmatched"`).

**Technical & Architectural Constraints (Codebase/Rust Expert):**
*   **Axum 0.8.9 Middleware:** Use Axum's `MatchedPath` extractor in a `tower` middleware to get the template of the route (e.g., `/api/files/:id` instead of `/api/files/123`). If `MatchedPath` is not present in the request extensions, default the label to `"unmatched"`.
*   **Registry Pattern:** Use the official `metrics` and `metrics-exporter-prometheus` crates. Avoid custom global static maps.

**Tech Lead Risk Synthesis & Mitigation:**
*   **Risk:** Axum middleware ordering is a notorious footgun. If the metrics middleware is applied globally via `axum::Router::layer()` at the wrong level, the `MatchedPath` extension won't be populated yet, causing *all* requests to be logged as `"unmatched"`.
*   **Mitigation:** The metrics middleware must be correctly attached using `tower::ServiceBuilder` *after* the routing layer has executed. I will mandate an integration test that fires requests at `/api/files/123` and verifies the Prometheus output specifically registers `route="/api/files/:id"` to prevent regressions.
```

## docs/backlog/003-prometheus-metrics-endpoint.md
```markdown
# Priority 3: Prometheus Metrics Endpoint

**Context:** Once the server is reporting health and our metric collection is safe from memory exhaustion, we can expose the endpoint. This allows advanced home-labbers and admins to pipe OxiCloud data into Grafana to identify sync bottlenecks.

**User Story:**
As a Server Admin, I want to scrape OxiCloud's performance data at `/metrics` so that I can visualize server load, API error rates, and database connection pool usage in my Grafana dashboard.

**Acceptance Criteria:**
```gherkin
Scenario: Fetching Prometheus metrics successfully
  Given OxiCloud is running and processing WebDAV/CalDAV sync requests
  When a Prometheus scraper makes a GET request to `/metrics`
  Then the server returns a 200 OK status code
  And the response body is formatted in valid Prometheus exposition plain-text format
  And the response includes active HTTP request counts mapped to static routes
  And the response includes PostgreSQL connection pool utilization metrics
```

**Security Constraints (Security Reviewer):**
*   **Information Leakage:** The `/metrics` endpoint is highly sensitive and exposes traffic patterns, API usage, and infrastructure loads. It must *not* be exposed to the public internet by default.
*   **Access Control:** The endpoint should ideally be served on a distinct, internal-only administrative port (e.g., `9090`), or locked behind a mandatory Bearer token / Basic Auth if on the main Axum port.

**Technical & Architectural Constraints (Codebase/Rust Expert):**
*   **Metrics Format:** Output must be rendered via `metrics_exporter_prometheus::PrometheusBuilder`.
*   **SQLx 0.8.6 Integration:** SQLx does not auto-publish Prometheus metrics by default. We must spawn a background Tokio task that periodically queries `pool.options().get_max_connections()`, `pool.size()`, and `pool.num_idle()` and writes them to the metrics registry (e.g., `gauge!("sqlx_pool_idle", pool.num_idle() as f64)`).

**Tech Lead Risk Synthesis & Mitigation:**
*   **Risk:** Mixing public endpoints with private infrastructure endpoints on the same Axum Router invites accidental exposure if authentication middleware is misconfigured or bypassed during a refactor.
*   **Mitigation:** We will implement the "Admin Server" pattern. The application will bind *two* `tokio::net::TcpListener`s. The main Axum router binds to the public port (e.g., `8080`), and a secondary, completely separate Axum router binds to a local-only or admin-configurable port (e.g., `127.0.0.1:9090`). `/metrics` (and potentially `/health`) will be mounted *exclusively* on the admin router, eliminating the need for complex auth middleware and perfectly securing it at the network boundary.
```
